# Nextflow on AWS Batch lab: rules for Kiro

This repository is a hands-on lab. The participant follows `docs/KIRO.md` and asks you to run the lab's own scripts and commands, then explain what happened. Run what exists and report the results. Do not build new infrastructure and do not improve the lab files.

## What each file is for

| File | Role | How you use it |
|---|---|---|
| `scripts/setup-nextflow-batch.sh` | One-shot, idempotent setup: installs Java 17 and Nextflow 24.10.5, deploys the CloudFormation stack `nextflow-batch` from `cfn/batch-nextflow.yaml`, writes `nextflow.config`, prepares `main.nf` and `/mnt/workflow/pubdir`. | Run it exactly as `bash scripts/setup-nextflow-batch.sh` from the repository root. Options are environment variables placed before the command (`WORK_BUCKET`, `DATA_BUCKET`, `MOUNT_DATA_BUCKET`, `MAX_VCPUS`). Running it again is safe. |
| `cfn/batch-nextflow.yaml` | The only CloudFormation template: IAM instance role, launch template, managed compute environment, job queue. | Deployed by the script only. Never deploy it yourself and never write another template. |
| `nextflow.config` | Generated by the script. Profile `batch`: executor `awsbatch`, queue `nextflow-batch-queue`, S3 work directory, AWS CLI path on the instances, cost tags. | Read it to answer questions. Never edit it; re-run the script if it must change. |
| `main.nf` | GreetingsNF, the same workflow the HealthOmics workshop registers. Publishes to `/mnt/workflow/pubdir`. | Run it. Never edit it. |
| `scripts/run-cost.py` | Cost estimate for a run from its trace file. | Run as `uv run --with boto3 scripts/run-cost.py <trace-file>` within an hour of the run. |
| `pipeline/ref-check.nf` | Optional Mountpoint for Amazon S3 example. Needs the stack deployed with `MOUNT_DATA_BUCKET=true`. | Run only when the participant asks for the Mountpoint section. |

## Never do these

1. Do not create, change or delete CloudFormation stacks except through `scripts/setup-nextflow-batch.sh`, and `aws cloudformation delete-stack --stack-name nextflow-batch` when the participant asks to clean up. No `aws cloudformation deploy`, `create-stack` or `update-stack` of your own, no CDK, no Terraform.
2. Do not change compute environment, job queue or job definition settings by hand (`aws batch update-compute-environment`, `register-job-definition` and similar). Nextflow registers job definitions itself.
3. Do not install, upgrade or switch Nextflow versions. The lab pins 24.10.5 because Nextflow 25 and later rejects `main.nf`. Do not run `curl -s https://get.nextflow.io | bash` and do not set `NXF_VER`.
4. Do not rewrite, patch or "fix" the scripts, the template, `main.nf` or `nextflow.config`. If a command fails, show the error and the lines of the file it points to, name the matching row in the README troubleshooting table if there is one, and stop. The participant decides what to do next.
5. Do not use `nohup nextflow ... &`. Nextflow reads the terminal and a plain background job gets stopped. To detach a long run, use Nextflow's own flag: `nextflow -bg run ... -ansi-log false > run.log 2>&1`, then follow `run.log` and `.nextflow.log`.
6. Do not print AWS account IDs, access keys, session tokens or the contents of `~/.aws/credentials`. The setup script prints the account ID once; do not repeat it in your answers. Never add `aws.accessKey` or `aws.secretKey` to any config file.
7. Do not delete the work bucket itself. Clean-up removes the `nextflow-batch/` prefix in that bucket, nothing else.
8. Do not run `aws` commands against a region other than `aws.region` in `nextflow.config`.

## Where to run things

Every command runs from the repository root, the directory that holds `main.nf` and the generated `nextflow.config`. Nextflow writes `.nextflow.log`, the trace files and `work/` metadata there. Published output goes to `/mnt/workflow/pubdir/output`; intermediate files go to `s3://<work bucket>/nextflow-batch/work/`. Use `-with-trace <file>` on every `nextflow run` so `run-cost.py` has a trace file to read; the lab names them `trace-cold.txt`, `trace-warm.txt`, `trace-bigger.txt`, `trace-sarek.txt`.

## Names used by the lab

| Thing | Name |
|---|---|
| CloudFormation stack | `nextflow-batch` |
| Job queue | `nextflow-batch-queue` |
| Compute environment | `nextflow-batch-ce-lt<N>`, where `<N>` is the launch template version |
| Job definitions | `nf-<image name>`, one per container image, created by Nextflow (for example `nf-public-ecr-aws-docker-library-ubuntu-22-04`) |
| Jobs | Named after the Nextflow process (`Greet`, `NFCORE_SAREK:SAREK:FASTQC`, ...) |
| Work directory | `s3://<work bucket>/nextflow-batch/work` |
| Region | `aws.region` in `nextflow.config` |

## Which tool to use

Use the shell for the lab commands: the setup script, `nextflow`, `aws` CLI commands and `run-cost.py`. Use the AWS MCP server (`aws-mcp`) for documentation lookups and for questions about AWS services, not for running lab steps. Read `nextflow.config`, `.nextflow.log` and the trace files before answering questions about a run, and quote the numbers you found (Duration, submit and start timestamps, instance type) with the file or command each came from.
